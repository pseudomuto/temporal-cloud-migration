Rehearsing the cloud gateway migration locally

Run the cloud gateway playbook end to end on one machine, with a second local Temporal Service standing in for Temporal Cloud.

What this is

Everything the playbook deploys runs here: Temporal Proxy in front of Cloud only, s2s-proxy carrying replication, and a pair of Temporal Services to migrate between. Apps talk to the self-hosted Temporal Service directly until their Namespace moves. The only stand-in is Cloud itself. Its side of replication needs an s2s-proxy inside the Cloud cell and the Cloud control plane to register the replica, neither of which runs on a laptop, so a local Temporal Service named cloud, and an s2s-proxy next to it, take their place.

Piece Runs as Address on your machine
Self-hosted Temporal Service, cluster self-hosted Docker, temporalio/server on sqlite localhost:17233
Stand-in for Temporal Cloud, cluster cloud. Namespace ns1 is ns1.acct there. Docker, same image localhost:27233
The playbook's s2s-proxy, holding the keys Docker, temporalio/s2s-proxy v0.3.1 metrics on localhost:19091
Stand-in for Cloud's s2s-proxy, no keys Docker, same image metrics on localhost:29091
Temporal Proxy, the gateway in front of cloud On the host, from Go source, so its codec server can sit on loopback and a restart is Ctrl-C gateway localhost:7233, codec server 127.0.0.1:8445, metrics 127.0.0.1:9090
Web UI straight at self-hosted, as apps see it before they flip Docker localhost:8082
Web UI through the gateway, as flipped apps see cloud Docker localhost:8080
Web UI straight at cloud, using the codec server Docker localhost:8081
The rehearsal Worker, one per Namespace On the host, from Go source connects to whatever you point it at

The configs follow the playbook's live config blocks, with three swaps: local addresses for Cloud's, no TLS or API key on the cloud upstream, and testing:// keys under static encryption.overrides for KMS. A testing:// key holds its key material in the URI, which is fine for throwaway local data and nothing else.

The client flip, which your routing layer does in production, is restarting a Namespace's Worker with a different TEMPORAL_ADDRESS. That's why each Namespace gets its own Worker process here: so each one can flip on its own.

If your proxies get keys from a KMS sidecar through extensionServers, this rehearsal checks what the keys and labels do, not how the sidecar picks them. If your sidecar picks a different key than the static overrides here would, this rehearsal won't show it.

What it covers, and what it can't

Playbook item Here
Phases 0 to 3, per Namespace, including the strict switch Yes
Key choice and binding labels, checked payload by payload Yes, with bin/payloads
The window between failover and the client flip Partly. It shows how the self-hosted Temporal Service forwards under the dcRedirectionPolicy you give it, with light traffic, not how Cloud forwards.
s2s-proxy failback Yes for payloads under a Namespace's own key, see Fail back a Namespace. Payloads under K_proxy aren't produced here, so opening them on the way back isn't shown.
Labels agree across the proxies Yes
What a refused replication message does to the stream The setup is here, but no known recipe produces opaque data. See Opaque data.
The Web UI through the gateway Not checked automatically. The steps say what each UI should show, but the UIs weren't driven in a browser while building this; the Cloud UI check was done through the codec server it calls, and the gateway's answers through the CLI.
Cloud's s2s-proxy config, API keys and TLS to Cloud, the Cloud UI, Cloud's forwarding, KMS permissions, a KMS sidecar, and the ListNamespaces rewrite No. These need a rehearsal against real Cloud, with the Cloud team setting up a migration endpoint for a test Namespace.

Prerequisites

  • Docker with Compose v2
  • Go 1.27 or later
  • The Temporal CLI, 1.9 or later
  • git, jq, openssl, and curl
  • Free ports: 7233, 8080, 8081, 8082, 8445, 9090, 17233, 19091, 27233, and 29091

These are the same ports the other rehearsal uses, so the two can't run at once. Tear one down before starting the other.

Every command below runs from cloud-gateway/rehearsal/ in a clone of this repository (see Set up), unless it says otherwise. Lines starting with $ are commands to run; type them without the $. You'll want five terminals: one for commands, one for Temporal Proxy, and one for each Namespace's Worker.

What's in this directory

Each path links to its source on GitHub.

The rehearsal Workflow

Rehearsal runs until it's signaled finish, so a Workflow started early is still running at every later phase. It runs the Echo Activity on its input every 15 seconds and on every ping signal, and the Fail Activity on every fail signal. That gives a steady supply of inputs, results, and failure messages to inspect.

Set up

Get the files. This page is part of a public repository; clone it and work from cloud-gateway/rehearsal/: 

$ git clone https://github.com/pseudomuto/temporal-cloud-migration.git
$ cd temporal-cloud-migration/cloud-gateway/rehearsal

Generate the configs and keys:

$ bin/gen-config

It writes generated/temporal-proxy.yaml, generated/s2s-self-hosted.yaml, and generated/s2s-cloud.yaml, and generates one key each for K_proxy, K_repl, and every Namespace into generated/keys. Keys are generated once and reused. Its settings (BINDING and the rest, described at the top of the script) are remembered between runs, so you only ever pass what changes. A handoff doesn't touch the configs: Temporal Proxy has no routing rules, and the flip happens in the Worker.

Start everything in Docker:

$ docker compose up -d --wait
Expect it to take a minute or two the first time. The last minute is s2s-proxy deliberately waiting for its mux connection before it serves; see Things worth knowing.

Connect the two Temporal Services through s2s-proxy. Each one is told to reach the other at its local s2s-proxy: 

$ temporal operator cluster upsert --address localhost:17233 \
    --frontend-address s2s-self-hosted:6233 --enable-connection
$ temporal operator cluster upsert --address localhost:27233 \
    --frontend-address s2s-cloud:6333 --enable-connection
$ temporal operator cluster list --address localhost:17233
Expect cloud listed at s2s-self-hosted:6233, next to self-hosted.

Phase 0: inventory and decisions

This is where the playbook takes stock of a real system. Here, it's where you build the "before" state: Namespaces in use, with cleartext history, and apps talking to the self-hosted Temporal Service directly.

Create the Namespaces, local to self-hosted for now:

$ for ns in ns1 ns2 ns3; do
    temporal operator namespace create --address localhost:17233 -n $ns --retention 72h
  done

Start one Worker per Namespace, against the self-hosted Temporal Service directly, each in its own terminal: 

$ cd worker
$ NAMESPACES=ns1 TEMPORAL_ADDRESS=localhost:17233 go run .

And the same with NAMESPACES=ns2 and NAMESPACES=ns3.

Start a Workflow in each Namespace:

$ for ns in ns1 ns2 ns3; do
    temporal workflow start --address localhost:17233 -n $ns \
      --type Rehearsal --task-queue rehearsal -w pre-1 --input '"secret before replication"'
  done
$ bin/payloads self-hosted ns1 pre-1
Expect every payload in json/plain, with no key and no label. Self-hosted stays this way for the whole migration: nothing seals in front of it. The Web UI at localhost:8082 should show it readable, with no codec server.

Promote the Namespaces to global. The playbook does this one Namespace at a time as each one's turn approaches; here, all three at once is fine: 

$ for ns in ns1 ns2 ns3; do
    temporal operator namespace update --address localhost:17233 -n $ns --promote-global
  done

Phase 1: put Temporal Proxy in front of Cloud

Start Temporal Proxy, in its own terminal:

$ go run go.temporal.io/proxy/cmd/proxy@v1.0.1 serve -c generated/temporal-proxy.yaml
Expect the gateway, codec server, and metrics listeners starting. The warnings about insecure credentials and an unauthenticated codec server are expected on loopback.

"Roll Temporal Proxy" from here on means Ctrl-C and run the same command again. Nothing calls it yet, so there's nothing to drain. 

$ bin/metrics
Expect every router_decisions_total series at zero. The only request is the gateway Web UI's health check.

Phase 2: replicate

Add cloud as a replica of each Namespace:

$ for ns in ns1 ns2 ns3; do
    temporal operator namespace update --address localhost:17233 -n $ns \
      --cluster self-hosted --cluster cloud
  done
$ until [ "$(temporal operator namespace list --address localhost:27233 -o json \
    | jq '[.[] | select(.namespaceInfo.name | endswith(".acct"))] | length')" = 3 ]; do sleep 1; done
$ temporal operator namespace list --address localhost:27233 -o json | jq -r '.[].namespaceInfo.name'
Expect ns1.acct, ns2.acct, and ns3.acct on cloud, after a few seconds. s2s-proxy's namespaceTranslation renamed them on the way. Wait for all three before the next step: replication of a Workflow that reaches cloud before its Namespace does is lost.

Replicate the Workflows that already exist. Adding a replica only replicates history written from then on. Existing Workflows need a force-replication run, which is the "let replication catch up" step in the playbook: 

$ for ns in ns1 ns2 ns3; do
    temporal workflow execute --address localhost:17233 -n temporal-system \
      --task-queue default-worker-tq --type force-replication -w force-replication-$ns \
      --input "{\"Namespace\":\"$ns\",\"OverallRps\":10}"
  done

Start one more Workflow, now that the replica exists:

$ temporal workflow start --address localhost:17233 -n ns1 \
    --type Rehearsal --task-queue rehearsal -w post-repl-1 --input '"secret after replication"'

Give it 20 seconds, then look at what cloud stores:

$ bin/payloads cloud ns1.acct pre-1
$ bin/payloads cloud ns1.acct post-repl-1
$ bin/metrics
Expect
  • Every payload in both Workflows binary/encrypted under repl. Nothing seals before s2s-proxy, so everything replicated before failover is under K_repl, not just the history from before replication started.
  • Every label ns1.acct.
  • No s2s-proxy counters listed. A labelled counter only appears once it has counted something, so absent means zero.

The Cloud UI check. Open localhost:8081, pick ns1.acct, and open pre-1. It should show readable payloads: the UI sends each payload to the codec server, naming ns1.acct, and the codec server holds K_repl. To check the codec server without a browser: 

$ temporal workflow show --address localhost:27233 -n ns1.acct -w pre-1 \
    --grpc-meta xdc-redirection=false -o json \
    | jq -c '{payloads: [.events[0].workflowExecutionStartedEventAttributes.input.payloads[0]]}' \
    | curl -s -X POST http://127.0.0.1:8445/decode -H 'Content-Type: application/json' \
        -H 'X-Namespace: ns1.acct' -d @-
Expect a json/plain payload whose data decodes (base64) to "secret before replication". Only K_repl payloads exist in cloud until the first failover, so this can't check a Namespace's own key yet; Phase 3 does.

Test the codec server by hand only under the name cloud uses. A decode request naming ns1 succeeds under permissive, but counts in vault_namespace_mismatches_total, which is one of the counters that has to be zero before strict.

Switch both proxies to strict, once the counters from Phase 2 are zero: 

$ BINDING=strict bin/gen-config
$ docker compose restart s2s-self-hosted && docker compose up -d --wait s2s-self-hosted

Then roll Temporal Proxy, and ping pre-1 on self-hosted:

$ temporal workflow signal --address localhost:17233 -n ns1 -w pre-1 --name ping --input '"ping under strict"'
$ bin/payloads cloud ns1.acct pre-1 | tail -3
$ bin/metrics
Expect the ping's events in cloud under repl, labelled ns1.acct, and still no s2s-proxy counters. Repeat the codec check: ns1.acct still decodes, and the same request naming ns1 now gets HTTP 400. Replication pauses for about a minute while s2s-proxy restarts.

Phase 3: hand off one Namespace

Start with ns1, and repeat for the others. The order is fail over, then flip.

Fail the Namespace over to cloud:

$ temporal operator namespace update --address localhost:17233 -n ns1 --active-cluster cloud

The window between failover and flip

ns1's Worker still polls self-hosted, where ns1 is now passive, and so does anything else that hasn't flipped. Leave it there on purpose, and send it work through self-hosted: 

$ temporal workflow start --address localhost:17233 -n ns1 \
    --type Rehearsal --task-queue rehearsal -w window-1 --input '"secret in the window"'
$ temporal workflow signal --address localhost:17233 -n ns1 -w pre-1 --name ping --input '"ping in the window"'

Give it 20 seconds:

$ bin/payloads cloud ns1.acct window-1
$ bin/payloads cloud ns1.acct pre-1 | tail -4
$ bin/payloads self-hosted ns1 window-1
Expect, with the shipped dcRedirectionPolicy: all-apis-forwarding:
  • The start and the signal succeed, and ns1's Worker runs both Workflows with no errors. The self-hosted Temporal Service forwards them, polls included, to cloud through s2s-proxy.
  • In cloud, window-1 and the new pre-1 events under ns:ns1, labelled ns1.acct: s2s-proxy sealed the forwarded calls with the Namespace's own key.
  • On self-hosted, window-1 in json/plain. s2s-proxy opens replication coming back in, and the Worker got plaintext through its forwarded polls.
Set the policy in temporal/self-hosted.yaml to whatever production uses before trusting this result.

Flipping first works here too, but don't count on it. A call through the gateway for a Namespace that hasn't failed over reaches its passive replica in cloud, which forwards it to self-hosted, because temporal/cloud.yaml also sets all-apis-forwarding. Temporal Proxy seals it, and s2s-proxy opens it on the way in. Whether real Cloud forwards to self-hosted this way isn't something this rehearsal can show; if it doesn't, clients that flip early get NamespaceNotActive. Failing over first leans only on forwarding you configure yourself.

Flip the clients

Restart ns1's Worker at the gateway: Ctrl-C it, and start it again with no address, which defaults to localhost:7233: 

$ NAMESPACES=ns1 go run .

Then work through the gateway:

$ temporal workflow start --address localhost:7233 -n ns1 \
    --type Rehearsal --task-queue rehearsal -w flip-1 --input '"secret after flip"'
$ temporal workflow signal --address localhost:7233 -n ns1 -w pre-1 --name ping --input '"ping after flip"'
$ temporal workflow signal --address localhost:7233 -n ns1 -w pre-1 --name fail --input '"card number 4111"'

Verify

$ bin/payloads cloud ns1.acct flip-1
$ bin/payloads cloud ns1.acct pre-1
$ bin/metrics
Expect
  • flip-1 under ns:ns1.
  • pre-1 mixing repl, for everything before failover, and ns:ns1 after it. Every label ns1.acct.
  • router_decisions_total{outcome="default",upstream="cloud"} climbing. With no rules, every Namespace counts under default.
  • server_requests_total all OK, and no unknown_key, mismatch, or unbound results in vault_ops_total.
  • Nothing in the Worker's log but the Activity error the fail signal asks for.

The first handoff is the first test of a Namespace's own key in cloud. Repeat the codec check from Phase 2 with a payload from flip-1: it should decode to "secret after flip". Or open it at localhost:8081. The gateway Web UI at localhost:8080 should show pre-1 readable all the way through, both keys, as the CLI through the gateway does.

Check failure sealing:

$ q='[.events[] | select(.eventType=="EVENT_TYPE_ACTIVITY_TASK_FAILED")][-1].activityTaskFailedEventAttributes.failure.message'
$ temporal workflow show --address localhost:7233 -n ns1 -w pre-1 -o json | jq -r "$q"
$ temporal workflow show --address localhost:27233 -n ns1.acct -w pre-1 \
    --grpc-meta xdc-redirection=false -o json | jq -r "$q"
Expect rehearsal failure: card number 4111 through the gateway, and Encoded failure as stored on cloud, with the real message sealed in encodedAttributes.

Fail back a Namespace

This rehearses the playbook's failback, and with it the "s2s-proxy failback" item. Hand off ns2 the same way as ns1, ping it, then undo it in reverse: flip the Worker back first, then fail back. 

$ temporal operator namespace update --address localhost:17233 -n ns2 --active-cluster cloud
# restart ns2's Worker with NAMESPACES=ns2 and no address
$ temporal workflow signal --address localhost:7233 -n ns2 -w pre-1 --name ping --input '"written on cloud"'
$ bin/payloads cloud ns2.acct pre-1 | tail -3

# restart ns2's Worker with NAMESPACES=ns2 TEMPORAL_ADDRESS=localhost:17233
$ temporal workflow signal --address localhost:17233 -n ns2 -w pre-1 --name ping --input '"flipped back, not failed back"'
$ bin/payloads cloud ns2.acct pre-1 | tail -3

$ temporal operator namespace update --address localhost:27233 -n ns2.acct --active-cluster self-hosted
$ temporal workflow signal --address localhost:17233 -n ns2 -w pre-1 --name ping --input '"back on self-hosted"'
$ bin/payloads self-hosted ns2 pre-1
$ bin/metrics
Expect
  • The "written on cloud" events in cloud under ns:ns2: Temporal Proxy sealed them.
  • The "flipped back, not failed back" signal in cloud under ns:ns2: with ns2 still active there, self-hosted forwarded it, as in the window after failover.
  • Every payload in self-hosted's pre-1 in json/plain, those included. s2s-proxy opened them on the way in, with ns2's key from its overrides.
  • Events written after failing back reach cloud under repl again.
  • No errors in bin/metrics or the Worker's log.

Opaque data

s2s-proxy runs with allowOpaquePlaintext: false, so any replication message carrying data it can't seal is refused and counted in enc_opaque_rejected_total. Which Temporal features produce such data on this server version is the open question, so there's no recipe here yet. To look for it, exercise the features you use in production on a replicated Namespace, and watch bin/metrics, the s2s-proxy log (docker compose logs -f s2s-self-hosted), and whether new history keeps reaching cloud. To see the other side of the setting, run ALLOW_OPAQUE_PLAINTEXT=true bin/gen-config and restart s2s-self-hosted, and opaque data is passed through and counted in enc_opaque_passthrough_total instead.

Reset and tear down

Stop the Workers and Temporal Proxy with Ctrl-C, then remove the containers. Each Temporal Service keeps its data inside its container, so this also wipes every Namespace and Workflow: 

$ docker compose down

To start over from Set up, also clear the generated configs and keys. Only ever delete the keys along with the Temporal Services' data, or the history they sealed stops opening: 

$ rm -rf generated

Things worth knowing

Found while building this, and worth carrying to the real migration:

  • Everything replicated before failover is under K_repl. With nothing sealing in front of self-hosted, every payload reaches cloud through s2s-proxy's replication key until its Namespace fails over. K_repl stays needed for as long as any Workflow running at failover is kept.
  • Forwarded calls use the Namespace's key. Calls self-hosted forwards to cloud after failover are sealed under ns:ns1, the same key Temporal Proxy uses after the flip.
  • Self-hosted stays readable. Before failover, during the window, and after failback, self-hosted holds plaintext, so tools reading it directly need no codec server.
  • Adding a replica doesn't backfill. Only history written after --cluster cloud replicates on its own. Workflows that already exist need force-replication.
  • Reads against a passive Namespace are forwarded. With forwarding on, reading ns1.acct's history from cloud before failover returns self-hosted's copy. Add --grpc-meta xdc-redirection=false to see what cloud really holds, which is what bin/payloads does.
  • Two rehearsals, one directory name. Both rehearsal directories are called rehearsal, which Compose uses as the project name by default. This one sets name: cloud-gateway-rehearsal so starting it can't replace the other's containers.
  • s2s-proxy takes a minute to serve. It binds its ports at once but waits a fixed minute (MuxManagerStartDelay) for its mux connection before serving them, so a port probe or pprof says it's ready too early. The compose healthcheck waits for its grpc_server_started metric instead.
  • A new remote cluster takes a while to be known. A Temporal Service reloads cluster metadata every minute by default, so a Namespace can't be replicated to a cluster added seconds ago (Invalid cluster name). The shared dynamic config here sets system.clusterMetadataRefreshInterval to 5 seconds.
  • Labelled counters only appear once incremented, in both proxies. A counter missing from /metrics is zero.

Troubleshooting

Symptom Likely cause
cluster upsert fails with context deadline exceeded s2s-proxy isn't serving yet. Rerun docker compose up -d --wait and try again.
Invalid cluster name: cloud The Temporal Service hasn't reloaded cluster metadata since the upsert. Wait 5 seconds and retry.
bin/payloads cloud ... says workflow not found The Workflow predates the replica and hasn't been force-replicated yet, or force-replication ran before the Namespace reached cloud. Run it again.
A Worker flipped before its Namespace failed over still works Expected here: cloud runs all-apis-forwarding, so it forwards calls for a passive Namespace to self-hosted. Real Cloud may not, and then they get NamespaceNotActive. Don't count on it; see Flipping first.
vault_ops_total{result="unknown_key"} A key one proxy sealed with isn't in the other's config. Configs from different generated/keys files, most likely.
vault_ops_total{result="mismatch"} under strict A label disagrees: a missing or wrong s2s-proxy mapping, or a decode request naming ns1 instead of ns1.acct.
A proxy refuses to start with duplicate key id The same key under two names. bin/gen-config won't do this; a hand-edited config might.
