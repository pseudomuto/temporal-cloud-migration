Playbook

Migrating to Temporal Cloud, with the gateway in front of Cloud only

Move Namespaces from a self-hosted Temporal Service to Temporal Cloud one at a time, with apps talking to the self-hosted Temporal Service directly until their Namespace moves, and without a payload reaching Cloud in cleartext.

Draft, 2026-10-29. The items under Confirm before starting haven't been tested end to end. A local rehearsal runs every phase on one machine.

Routing every Worker and Client through Temporal Proxy from the start, and handing off by removing a routing rule? Use the playbook for a gateway in front of both Temporal Services instead.

How to use this playbook

This page is an interactive playbook, not just a doc. Keep it open throughout the migration and use it to track your progress.

  • Fill in your details in the box below. Your account suffix, Namespace list, and KMS key pattern feed the config blocks marked live, so you can copy them as-is.
  • Tick steps as you finish them. The sidebar shows how many steps are done in each section.
  • Drive handoffs from the Phase 3 tracker. It has one row per Namespace, flags anything out of order, and suggests what to do next.
  • Step through the diagram to see how traffic moves in each phase.

Progress is saved in this browser's local storage. Nothing is sent anywhere, so it isn't shared with teammates and won't follow you to another browser or machine. Clearing site data deletes it, and Reset progress in the sidebar wipes it intentionally.

Config blocks marked live are generated from these and from your progress below. Prose uses ns1 as the example. Everything you enter or tick is saved in this browser only.

Three pieces share the work:

  • Your routing layer (DNS, service discovery, or config) decides which Temporal Service each app talks to. Apps keep talking to the self-hosted Temporal Service directly until their Namespace moves. Handing a Namespace to Cloud is failing it over, then flipping that Namespace's Workers and Clients to the gateway.
  • Temporal Proxy is the gateway in front of Cloud, and only Cloud. It seals Worker and Client traffic for every Namespace whose apps have flipped. It has no routing rules, and a handoff doesn't change its config.
  • s2s-proxy carries replication between the two Temporal Services, sealing admin traffic and replication streams on the way out and opening them on the way in.

The Temporal side of replication (connecting the Temporal Services through s2s-proxy, adding Cloud as a replica of each Namespace, and failing a Namespace over) is summarized here, not specified.

Common questions

Teams with this setup tend to ask these first:

  • Fail over first, or flip clients first? Fail over first. See Why fail over first.
  • Can replicated history be sealed per Namespace? Not today: everything replicated before a Namespace fails over is under the shared K_repl. See Keys.
  • Start on permissive, then switch to strict before the first handoff? Yes, and strict costs less here than with a gateway in front of both. See Namespace binding.
  • What does failback need on the Cloud side? Nothing beyond what's already in place, but flip clients back before failing back. See Failback.
  • What should we monitor? See Monitoring.

Assumptions

  • Temporal Proxy is at v1.0.0 or later. That release has encryption.failures and encryption.namespaceBinding, which the playbook relies on.
  • s2s-proxy is at v0.3.1 or later. It seals admin calls and replication streams, seals failure messages and stack traces as Temporal Proxy does, and binds payloads to the Namespace's name on the peer. Either proxy opens what the other sealed.
  • Each Namespace's Cloud name is its local name plus the account suffix (e.g., ).
  • Your routing layer can move one Namespace's Workers and Clients without moving the others. See Phase 0.
  • The configs here use static encryption.overrides. If your proxies get keys from a KMS sidecar through extensionServers, it has to pick the same key for each payload that the overrides here would.

What "no plaintext" covers

Both proxies seal payloads (Workflow and Activity inputs and results, signal and update arguments, memo, heartbeat details) and failure messages and stack traces. That is the guarantee: none of those reaches Cloud readable.

It is not a guarantee about the self-hosted Temporal Service. Nothing seals in front of it, so it stores plaintext for the whole migration, as it does today, and after a failback too.

It also doesn't cover what a Temporal Service needs to read to do its job, which crosses as is:

  • Metadata. Workflow IDs, run IDs, Workflow and Activity type names, task queue names, Namespace names, timestamps, and retry policies.
  • Search attribute values. Both proxies skip search attributes when sealing, because Cloud has to read them to answer visibility queries. Anything sensitive in a search attribute crosses in the clear. Audit them before starting.
  • Opaque admin data, covered under Phase 0. This is the one case where the guarantee is enforced by refusing to replicate, not by sealing.

How the pieces fit

Both proxies sit inside the self-hosted network, and the thick edges are the only paths into Cloud. Start from the initial state and move through each phase to see how traffic moves. Phase 3 follows the handoff tracker.

Every label is the Cloud name, , whoever sealed the payload. Every sealed payload names the KEK that wrapped its DEK, and opening looks the KEK up by that ID across every key the vault holds. So a key only needs to be listed somewhere in a proxy's config to be usable for opening; the Namespace it's listed under doesn't matter.

Keys

Each migrating Namespace gets its own KMS key, K_ns1 through K_ns5. Two shared keys sit beside them:

  • K_ns1 and the rest, under encryption.overrides in both proxies, keyed by the local Namespace name. Temporal Proxy seals the Namespace's Worker and Client traffic with it after the flip, and s2s-proxy seals the calls it forwards for that Namespace after failover.
  • K_proxy, Temporal Proxy's encryption.default.uri. A default key is required, and it seals anything without an override: a Namespace created during the migration, a typo, and calls that don't name a Namespace.
  • K_repl, s2s-proxy's encryption.default.uri. Replication is sealed under it.

Replication isn't sealed per Namespace. s2s-proxy seals every admin message, replication included, under its replication key, whatever Namespace the task belongs to (replicationKey in interceptor/admin_encryptor.go). It knows each task's Namespace for binding, but not for choosing a key. With nothing sealing in front of the self-hosted Temporal Service, every payload replicated before a Namespace fails over reaches Cloud under the shared K_repl, history written yesterday included, not just history from before replication started.

That has two consequences. Revoking K_ns1 doesn't make that Namespace's pre-failover history unreadable; only revoking K_repl does, and that covers every Namespace. And K_repl stays in use for longer: until every Workflow running at its Namespace's failover has closed, and retention has passed since. See Phase 4.

Both configs carry the same overrides

The two override maps must be identical: same Namespaces, same key URIs. A Namespace missing from s2s-proxy's map has its forwarded calls sealed under K_repl instead of its own key. One whose key differs is sealed under a key the other proxy may not hold, which fails with vault_ops_total{result="unknown_key"}. Temporal Proxy needs K_repl because, once a Namespace's apps flip, everything replicated before its failover is under it. Without it, those payloads fail with vault_ops_total{result="unknown_key"}. s2s-proxy needs K_proxy only for failback, to open anything Temporal Proxy sealed under its default on the way back into the self-hosted Temporal Service.

No key may appear twice in one proxy's config, across default, overrides, and every decryptURIs: both proxies refuse to start with duplicate key id. That is why each Namespace needs a distinct key, and why s2s-proxy sets no replication policy: without one, admin traffic is sealed under default, which is already K_repl.

Namespace binding

With binding on, each sealed payload is labelled with a Namespace name, and under strict it opens only for that Namespace. Both proxies label with the name Cloud knows, :

  • Temporal Proxy labels with the Namespace's name on its only upstream, cloud, after the suffix rule. It needs no bindingLabelsFrom, since nothing routes to the self-hosted Temporal Service through it.
  • s2s-proxy labels with the Namespace's name on the peer, from its namespaceTranslation mappings. Replication tasks name their Namespace by ID, which s2s-proxy resolves with DescribeNamespace on the self-hosted Temporal Service.

Both keys are new, and both proxies label from the first payload they seal, so no unlabelled payload ever reaches Cloud. That is what lets the migration reach strict without the usual wait for unlabelled history to age out.

permissivePhase 1 and Phase 2. Mistakes show up as counters instead of refusals.
strictBefore the first handoff, once the Phase 2 counters stay at zero. No retention wait.
strictPhase 3 onward, for every handoff and after.

What strict costs during the migration

Less than with a gateway in front of both Temporal Services. Tools that read the self-hosted Temporal Service directly see plaintext, so they need no codec server and can't hit a label mismatch.

  • Cross-Namespace traffic is refused. See Phase 0. If any exists, both proxies stay on permissive.
  • Tools that read Cloud directly need the codec server, under the Cloud name. A request naming ns1 gets HTTP 400. The CLI can name the Cloud name in the codec endpoint path, which takes precedence over the X-Namespace header it sends; use the literal name, not {namespace}:
    Or point the tool at the gateway, where Temporal Proxy opens payloads on the way back and no codec server is involved.
  • Mistakes become outages. A Namespace missing from s2s-proxy's namespaceTranslation is labelled ns1, and Temporal Proxy refuses its replicated history once apps flip. If s2s-proxy can't resolve a Namespace ID, it fails the replication message and, with it, the stream. permissive would fall back to the replication key's name and count it. The Phase 2 soak exists to catch both.

Teams that know they have no cross-Namespace traffic can start on strict, but keep the Phase 2 soak: it's the only check for unresolved Namespace IDs and missing mappings before they become refusals.

Phase 0: inventory and decisions

Do these before touching any traffic.

  1. List the Namespaces: 
    temporal operator namespace list --address temporal.internal:7233 -o json \
  | jq -r '.[] | [.namespaceInfo.name, .namespaceInfo.state, (.isGlobalNamespace // false)] | @tsv'
    Example output
    default          NAMESPACE_STATE_REGISTERED  false
temporal-system  NAMESPACE_STATE_REGISTERED  false
ns1              NAMESPACE_STATE_REGISTERED  false
...
    Reading the output
    • temporal-system belongs to the Temporal Service itself. It never migrates.
    • default exists on every Temporal Service. It migrates like any other Namespace if something uses it, and can be left out otherwise.
    • NAMESPACE_STATE_DEPRECATED Namespaces refuse new Workflows but still hold running ones, so decide whether each one moves or drains in place.
    • The third column says whether the Namespace is global. Only global Namespaces replicate, so any false that is migrating gets promoted in the last step here.
    Enter the result in Namespaces to migrate at the top.
  2. Check that every app can flip one Namespace at a time. For each Namespace, list the Workers and Clients that use it and how your routing layer points them at a Temporal Service. A process that serves several Namespaces through one address can't move one of them alone: when that address flips, every Namespace it serves follows, failed over or not. For each such process, choose one:
    • Give it one address per Namespace, so each can flip on its own.
    • Hand off its Namespaces together, as one step.
    • Split it, so each Namespace has its own Workers and Clients.
  3. Find opaque admin data. Some admin data can't be sealed: HSM and CHASM state, serialized tasks, and the like, which the receiving Temporal Service decodes itself. With encryption.allowOpaquePlaintext off, which "no plaintext" requires, s2s-proxy refuses any message carrying it.

    A refused unary call fails with Internal. A refused replication stream message ends the whole stream, not just the affected Workflow's part of it, and the peer sees Internal with "s2s-proxy could not seal or open a replication message; see its logs".

    s2s-proxy counts each refusal in enc_opaque_rejected_total, labelled by kind, and logs the kind and the field path. Neither names the Namespace or the Workflow, and since the stream ends, unrelated Workflows stall alongside the one that caused it. Find the cause from the Temporal side, from the replication tasks stuck at the head of the stalled stream.

    For each Namespace that turns up here, choose one:
    • Stop the feature producing it, and let the affected Workflows finish on the self-hosted side before failover.
    • Accept that those Workflows don't migrate.
    • Grant an exception and set allowOpaquePlaintext. It is a single s2s-proxy setting, so the exception covers every Namespace replicating through it.
    The counter only moves once replication is running, so the real inventory comes from Phase 2 with failover held back. Plan for this to be the step that sets the schedule.
  4. Audit search attributes for sensitive values, as above.
  5. Find cross-Namespace traffic: child Workflows started in another Namespace, signals sent from one, and Nexus operations that cross Namespaces. Their payloads carry the other Namespace's label, which strict refuses. Temporal Proxy exempts Nexus but not the other two; s2s-proxy exempts none of them. Binding is one setting per proxy, so if any of this exists, both proxies stay on permissive for every Namespace, not just the ones involved.
  6. Check the self-hosted Temporal Service's dcRedirectionPolicy. Between a Namespace's failover and its flip, apps still on self-hosted depend on it forwarding their calls, polls included, to Cloud. See The window.
  7. Record each Namespace's retention period. The longest one decides when K_repl can be retired.
  8. Prepare both sides for replication. Promote every migrating Namespace that isn't global yet with temporal operator namespace update -n ns1 --promote-global. Promotion is one-way, so do it per Namespace as its turn approaches, not all at once. Then create the Cloud Namespaces as replicas, named , and an API key for Temporal Proxy. Create the KMS keys too: K_proxy, K_repl, and one per Namespace from the key map. Grant each proxy only what Who holds what lists.

Phase 1: put Temporal Proxy in front of Cloud

Deploy Temporal Proxy with encryption on. It has one job, reaching Cloud, so it has no routing rules: every Namespace goes to the cloud upstream, and Namespace-less calls to cloud-system. Nothing calls it yet. This block tracks your progress: namespaceBinding flips once you switch to strict, and nothing else changes for the rest of the migration.

Phase 2: replicate

Configure s2s-proxy's cluster connection. Encryption and Namespace translation are both per connection:

s2s-proxy cluster connectionlive

Everything s2s-proxy replicates is sealed under K_repl on its way out and labelled . It looks up each replication task's Namespace ID with DescribeNamespace on the self-hosted Temporal Service, and caches the answer per connection for five minutes. Whatever credentials it uses there must allow that call.

On the Temporal side: connect the two Temporal Services through s2s-proxy, add Cloud as a replica of each Namespace, and let replication catch up. Adding a replica only replicates history written from then on; existing Workflows need a force-replication run.

Before switching to strict, which is before the first handoff

  1. enc_unresolved_namespaces_total on s2s-proxy has stayed at zero since replication started. Each increment is a payload labelled with the replication key's name instead of its Namespace's, which strict would refuse when it is read back. If it moved, fix the cause and judge readiness only on payloads sealed after that.
  2. enc_unbound_opens_total and enc_namespace_mismatches_total on s2s-proxy, and vault_unbound_opens_total and vault_namespace_mismatches_total on Temporal Proxy, are at zero.
  3. For each Namespace, a replicated Workflow opens in the Cloud UI with Temporal Proxy's codec server configured. That proves K_repl opens and that s2s-proxy's mapping matches Temporal Proxy's suffix rule. Only K_repl payloads exist in Cloud until the first failover, so the Namespace's own key is first checked at handoff.
  4. Set namespaceBinding: strict on both proxies and roll them. Switching back to permissive is always safe. Ticking this updates both live config blocks.

Before each handoff

  • enc_opaque_rejected_total and enc_admin_visit_failures_total are zero, or every refusal has a decision from Phase 0.
  • Replication lag is near zero.
  • The Cloud UI check above passes for this Namespace.
  • You know which Workers and Clients flip for this Namespace, and how.

These are the Conditions column in the Phase 3 tracker.

Why fail over first

Either order leans on forwarding for a while, in opposite directions:

  • Fail over, then flip. Until the flip, apps still on self-hosted reach a Namespace that is now passive there. They keep working only if the self-hosted Temporal Service forwards their calls to Cloud. That's a setting you control, and the rehearsal shows it working under all-apis-forwarding, polls included.
  • Flip, then fail over. Until the failover, flipped apps reach a Namespace that is still passive in Cloud. They keep working only if Cloud forwards their calls back to the self-hosted Temporal Service; otherwise they get NamespaceNotActive. You don't control that, and the rehearsal can't show it.

So fail over first, and keep the window between the two steps short.

The window between failover and flip

After failover, the self-hosted Temporal Service forwards calls for the Namespace to Cloud through s2s-proxy, which seals them with the Namespace's own key, K_ns1, from its overrides, labelled . Responses come back through s2s-proxy and are opened on the way in, so apps still on self-hosted keep seeing plaintext, and so does the self-hosted Temporal Service's passive copy of the history.

Watch during the window:

  • The self-hosted Temporal Service's request errors for the Namespace, by status. NamespaceNotActive means a call isn't being forwarded.
  • Whether Workers still on self-hosted keep completing tasks. A policy that doesn't forward polls would likely leave them idle until they flip; that's untested, see Confirm before starting.
  • s2s-proxy's enc_namespace_mismatches_total and enc_admin_visit_failures_total, and Temporal Proxy's vault_ops_total{result="unknown_key"}.

Failback

Failback is the handoff in reverse: flip the Namespace's Workers and Clients back to the self-hosted frontend, then fail the Namespace back to the self-hosted Temporal Service. In the tracker, untick the Namespace's steps from right to left.

The order matters for the same reason as in Why fail over first. Flipping back first puts apps on self-hosted while the Namespace is still active in Cloud, which leans on the self-hosted Temporal Service forwarding to Cloud: the same forwarding the handoff window uses. Failing back first would leave apps on the gateway pointed at a Namespace now passive in Cloud, which works only if Cloud forwards to self-hosted.

  • Nothing else is needed on the Cloud side. Cloud keeps its copy of the history sealed. Temporal Proxy's config doesn't change.
  • s2s-proxy opens payloads on the way in, Temporal Proxy's included. It holds each Namespace's key through its override, and K_proxy for unwrap. So the self-hosted Temporal Service holds plaintext again, history written in Cloud included.
  • History written after failback replicates under K_repl again. The K_repl retirement clock in Phase 4 restarts from the Namespace's next failover.

The rehearsal shows this, in this order, for payloads under a Namespace's own key. Payloads under K_proxy on the way back are untested; see Confirm before starting.

Phase 4: finish

  1. Disconnect replication and retire s2s-proxy, once you no longer want failback.
  2. Keep K_repl in Temporal Proxy's decryptURIs. Every payload replicated before its Namespace's failover is sealed with it, and labelled for its Namespace, so strict opens it.
  3. Retire K_repl once nothing sealed with it remains: every Workflow running at its Namespace's failover has closed, and the longest retention period from Phase 0 has passed since, plus anything you still read from archives. A long-running Workflow keeps its K_repl payloads for as long as it runs.

End state

With the self-hosted Temporal Service and s2s-proxy gone, Temporal Proxy is the only path to Cloud:

Workers and Clients point at the gateway, with the same short Namespace names they used against the self-hosted Temporal Service. Temporal Proxy's config is the one from Phase 1. It still holds K_repl for unwrap until Phase 4 retires it.

Confirm before starting

These are assumptions the playbook leans on that haven't been tested end to end. Tick each once a rehearsal against real Cloud has shown it. The local rehearsal covers some of them partly, as noted.

  • Forwarding from a passive Namespace. Which calls the self-hosted Temporal Service forwards to Cloud after failover, polls in particular, under your production dcRedirectionPolicy and real load. The local rehearsal shows it working under all-apis-forwarding with light traffic, against a local stand-in for Cloud.
  • What Cloud does with calls for a passive Namespace. Whether apps that flip before failover get NamespaceNotActive or are forwarded to the self-hosted Temporal Service. The playbook doesn't depend on it, since it fails over first, but a flip that runs early for one app hits it. The local stand-in forwards, which says nothing about Cloud.
  • s2s-proxy failback under K_proxy. That payloads Temporal Proxy sealed under K_proxy open on their way back into the self-hosted Temporal Service, with s2s-proxy holding K_proxy for unwrap only. The local rehearsal shows failback for payloads under a Namespace's own key, not this.
  • What a refused replication message does to the stream. s2s-proxy ends the stream with Internal. That the Temporal Service then reconnects and retries the same message, stalling everything behind it on that stream until the cause is fixed, is inferred, not observed.
  • The Web UI works fully through the gateway. Browsing, decoding, starting and signaling Workflows, and the Namespace list through cloud-system. Also check that the UI server calls nothing beyond WorkflowService and OperatorService, the gateway's default service allowlist.
  • A KMS sidecar picks the same keys. If your proxies use one through extensionServers, that it seals each payload under the key the overrides here would. The local rehearsal uses static overrides.
