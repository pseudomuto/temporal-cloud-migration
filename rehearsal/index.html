Rehearsing the migration locally

Run the migration playbook end to end on one machine, with a second local Temporal Service standing in for Temporal Cloud.

What this is

Everything the playbook deploys runs here: Temporal Proxy in front of the Workers, s2s-proxy carrying replication, and a pair of Temporal Services to migrate between. The only stand-in is Cloud itself. Its side of replication needs an s2s-proxy inside the Cloud cell and the Cloud control plane to register the replica, neither of which runs on a laptop, so a local Temporal Service named cloud, and an s2s-proxy next to it, take their place.

Piece Runs as Address on your machine
Self-hosted Temporal Service, cluster self-hosted Docker, temporalio/server on sqlite localhost:17233
Stand-in for Temporal Cloud, cluster cloud. Namespace ns1 is ns1.acct there. Docker, same image localhost:27233
The playbook's s2s-proxy, holding the keys Docker, built from source metrics on localhost:19091
Stand-in for Cloud's s2s-proxy, no keys Docker, same image metrics on localhost:29091
Temporal Proxy, the gateway Workers use On the host, from Go source, so its codec server can sit on loopback and a restart is Ctrl-C gateway localhost:7233, codec server 127.0.0.1:8445, metrics 127.0.0.1:9090
Web UI through the gateway Docker localhost:8080
Web UI straight at cloud, using the codec server Docker localhost:8081
The rehearsal Worker On the host, from Go source connects to whatever you point it at

The configs follow the playbook's live config blocks, with three swaps: local addresses for Cloud's, no TLS or API key on the cloud upstream, and testing:// keys for KMS. A testing:// key holds its key material in the URI, which is fine for throwaway local data and nothing else.

What it covers, and what it can't

Playbook item Here

Key choice and binding labels, checked payload by payload Yes, with bin/payloads

s2s-proxy failback Yes, see Roll back a handoff
Labels agree across the proxies Yes

The Web UI through the gateway Yes

Prerequisites

  • Docker with Compose v2
  • Go 1.27 or later
  • The Temporal CLI, 1.9 or later
  • git, jq, openssl, and curl
  • Free ports: 7233, 8080, 8081, 8445, 9090, 17233, 19091, 27233, and 29091

Every command below runs from rehearsal/ in a clone of this repository (see Set up), unless it says otherwise. Lines starting with $ are commands to run; type them without the $. You'll want three terminals: one for commands, one for the Worker, and one for Temporal Proxy.

The rehearsal Workflow

Rehearsal runs until it's signaled finish, so a Workflow started early is still running at every later phase. It runs the Echo Activity on its input every 15 seconds and on every ping signal, and the Fail Activity on every fail signal. That gives a steady supply of sealed inputs, results, and failure messages to inspect.

Set up

Get the files. This page is part of a public repository; clone it and work from rehearsal/: 

$ git clone https://github.com/pseudomuto/temporal-cloud-migration.git
$ cd temporal-cloud-migration/rehearsal

Build s2s-proxy. The playbook needs #322 to #326, which are stacked and unmerged, and temporal-proxy v1.0.0, which merged after the stack was cut. This clones s2s-proxy into .work/, checks out the top of the stack, and merges main into it: 

$ bin/prepare-s2s-proxy
Expect the commits it built from, and temporal-proxy: go.temporal.io/proxy v1.0.0 or later. A merge conflict stops it with git's own message. Once the stack merges, run it with S2S_PROXY_STACK=main.

Generate the configs and keys:

$ bin/gen-config

It writes generated/temporal-proxy.yaml, generated/s2s-self-hosted.yaml, and generated/s2s-cloud.yaml, and generates one key each for K_proxy, K_repl, and every Namespace into generated/keys. Keys are generated once and reused. Its settings (BINDING, HANDED_OFF, and the rest, described at the top of the script) are remembered between runs, so you only ever pass what changes.

Start everything in Docker:

$ docker compose up -d --build --wait
Expect it to take a minute or two the first time. The last minute is s2s-proxy deliberately waiting for its mux connection before it serves; see Things worth knowing.

Connect the two Temporal Services through s2s-proxy. Each one is told to reach the other at its local s2s-proxy: 

$ temporal operator cluster upsert --address localhost:17233 \
    --frontend-address s2s-self-hosted:6233 --enable-connection
$ temporal operator cluster upsert --address localhost:27233 \
    --frontend-address s2s-cloud:6333 --enable-connection
$ temporal operator cluster list --address localhost:17233
Expect cloud listed at s2s-self-hosted:6233, next to self-hosted.

Phase 0: inventory and decisions

This is where the playbook takes stock of a real system. Here, it's where you build the "before" state: Namespaces in use, with cleartext history, and nothing in front of the self-hosted Temporal Service.

Create the Namespaces, local to self-hosted for now:

$ for ns in ns1 ns2 ns3; do
    temporal operator namespace create --address localhost:17233 -n $ns --retention 72h
  done

Start the Worker against the self-hosted Temporal Service directly, in the Worker terminal, as every Worker runs before the migration: 

$ cd worker
$ TEMPORAL_ADDRESS=localhost:17233 go run .

Start a Workflow in each Namespace, still directly:

$ for ns in ns1 ns2 ns3; do
    temporal workflow start --address localhost:17233 -n $ns \
      --type Rehearsal --task-queue rehearsal -w pre-1 --input '"secret before phase 1"'
  done
$ bin/payloads self-hosted ns1 pre-1
Expect every payload in json/plain, with no key and no label. This is the history the playbook says reaches Cloud under K_repl.

Promote the Namespaces to global (Phase 0, step 6). The playbook does this one Namespace at a time as each one's turn approaches; here, all three at once is fine: 

$ for ns in ns1 ns2 ns3; do
    temporal operator namespace update --address localhost:17233 -n $ns --promote-global
  done

Phase 1: put Temporal Proxy in front

Start Temporal Proxy, in its own terminal:

$ go run go.temporal.io/proxy/cmd/proxy@v1.0.1 serve -c generated/temporal-proxy.yaml
Expect one Registering crypto key line per key, and the gateway, codec server, and metrics listeners starting. The warnings about insecure credentials and an unauthenticated codec server are expected on loopback.

"Roll Temporal Proxy" from here on means Ctrl-C and run the same command again. It drains in-flight calls for 5 seconds, then drops the rest; Workers re-poll on their own.

Move the Worker to the gateway: Ctrl-C it, and start it again with no address, which defaults to localhost:7233: 

$ go run .

Make sure the direct Worker is really gone. A Worker still polling the self-hosted Temporal Service directly writes cleartext, and when it picks up a Workflow started through the gateway, it can't decode the sealed input: the Go SDK fails that Workflow execution outright, with payload encoding is not supported. Try it on a throwaway Workflow if you want to see it.

Start a Workflow through the gateway:

$ temporal workflow start --address localhost:7233 -n ns1 \
    --type Rehearsal --task-queue rehearsal -w post-1 --input '"secret after phase 1"'

Give both Workflows 20 seconds, then look at what self-hosted stores:

$ bin/payloads self-hosted ns1 pre-1
$ bin/payloads self-hosted ns1 post-1
$ bin/metrics
Expect
  • pre-1: event 1 still json/plain; every later payload binary/encrypted under ns:ns1.
  • post-1: everything sealed under ns:ns1.
  • Every label ns1.acct, not ns1. That's bindingLabelsFrom: cloud at work.
  • router_decisions_total{outcome="match",upstream="self-hosted"} climbing, and nothing at all with upstream="cloud" but zeros.

The Web UI through the gateway, at localhost:8080, shows ns1, ns2, and ns3 with readable payloads and no codec server.

Phase 2: replicate

Add cloud as a replica of each Namespace:

$ for ns in ns1 ns2 ns3; do
    temporal operator namespace update --address localhost:17233 -n $ns \
      --cluster self-hosted --cluster cloud
  done
$ until [ "$(temporal operator namespace list --address localhost:27233 -o json \
    | jq '[.[] | select(.namespaceInfo.name | endswith(".acct"))] | length')" = 3 ]; do sleep 1; done
$ temporal operator namespace list --address localhost:27233 -o json | jq -r '.[].namespaceInfo.name'
Expect ns1.acct, ns2.acct, and ns3.acct on cloud, after a few seconds. s2s-proxy's namespaceTranslation renamed them on the way. Wait for all three before the next step: replication of a Workflow that reaches cloud before its Namespace does is lost.

Replicate the Workflows that already exist. Adding a replica only replicates history written from then on. Existing Workflows need a force-replication run, which is the "let replication catch up" step in the playbook: 

$ for ns in ns1 ns2 ns3; do
    temporal workflow execute --address localhost:17233 -n temporal-system \
      --task-queue default-worker-tq --type force-replication -w force-replication-$ns \
      --input "{\"Namespace\":\"$ns\",\"OverallRps\":10}"
  done

Look at what cloud stores:

$ bin/payloads cloud ns1.acct pre-1
$ bin/payloads cloud ns1.acct post-1
$ bin/metrics
Expect
  • pre-1 event 1 sealed under repl: written before Phase 1, so s2s-proxy sealed it on the way out.
  • Every other payload, in both Workflows, still under ns:ns1: Temporal Proxy sealed them, and s2s-proxy passed them through.
  • Every label ns1.acct.
  • No s2s-proxy counters listed. A labelled counter only appears once it has counted something, so absent means zero.

The Cloud UI check. Open localhost:8081, pick ns1.acct, and open pre-1 and post-1. Both should show readable payloads: the UI sends each payload to the codec server, naming ns1.acct, and the codec server opens both keys. This is the check the playbook says nothing else makes before handoff.

Test the codec server by hand only under the name cloud uses. A decode request naming ns1 succeeds under permissive, but counts in vault_namespace_mismatches_total, which is one of the counters that has to be zero before strict.

Switch both proxies to strict, once the counters from Phase 2 are zero: 

$ BINDING=strict bin/gen-config
$ docker compose restart s2s-self-hosted && docker compose up -d --wait s2s-self-hosted

Then roll Temporal Proxy, and ping both Workflows:

$ temporal workflow signal --address localhost:7233 -n ns1 -w pre-1 --name ping --input '"ping under strict"'
$ temporal workflow signal --address localhost:7233 -n ns1 -w post-1 --name ping --input '"ping under strict"'
$ bin/metrics
Expect both pings echoed in the Worker's history, only result="success" in vault_ops_total, and the UI at localhost:8081 still decoding. Replication pauses for about a minute while s2s-proxy restarts.

Phase 3: hand off one Namespace

Start with ns1, and repeat for the others.

Fail the Namespace over to cloud:

$ temporal operator namespace update --address localhost:17233 -n ns1 --active-cluster cloud

Before rolling, watch the gap. Temporal Proxy still routes ns1 to self-hosted, where it's now passive. This is the playbook's "Forwarding from a passive Namespace" item: 

$ temporal workflow signal --address localhost:7233 -n ns1 -w post-1 --name ping --input '"between failover and roll"'
$ temporal workflow show --address localhost:7233 -n ns1 -w post-1 -o json \
    | jq -r '.events[-6:][] | "\(.eventId) v\(.version) \(.eventType)"'
Expect, with the shipped dcRedirectionPolicy: all-apis-forwarding, no errors in the Worker, and the new events at v2, meaning cloud wrote them. The self-hosted Temporal Service forwarded the Worker's polls and completions to cloud through s2s-proxy. Set the policy in temporal/self-hosted.yaml to whatever production uses before trusting this result.

Remove the routing rule and roll Temporal Proxy:

$ HANDED_OFF=ns1 bin/gen-config

Then roll Temporal Proxy. To prove the old history opens from cloud, restart the Worker too: with its cache empty, it replays pre-1 from the start, including the event sealed under K_repl. 

$ temporal workflow signal --address localhost:7233 -n ns1 -w pre-1 --name ping --input '"ping after handoff"'
$ temporal workflow signal --address localhost:7233 -n ns1 -w pre-1 --name fail --input '"card number 4111"'
$ bin/metrics
Expect
  • router_decisions_total{outcome="default",upstream="cloud"} climbing.
  • No unknown_key, mismatch, or unbound results in vault_ops_total.
  • The ping echoed, and nothing in the Worker's log but the Activity error the fail signal asks for.

Check failure sealing:

$ q='[.events[] | select(.eventType=="EVENT_TYPE_ACTIVITY_TASK_FAILED")][-1].activityTaskFailedEventAttributes.failure.message'
$ temporal workflow show --address localhost:7233 -n ns1 -w pre-1 -o json | jq -r "$q"
$ temporal workflow show --address localhost:27233 -n ns1.acct -w pre-1 \
    --grpc-meta xdc-redirection=false -o json | jq -r "$q"
Expect rehearsal failure: card number 4111 through the gateway, and Encoded failure as stored on cloud, with the real message sealed in encodedAttributes (bin/payloads lists it).

Roll back a handoff

This rehearses the playbook's rollback, and with it the "s2s-proxy failback" item. Hand off ns2 the same way as ns1, ping it, then undo it in the same order: fail back first, then roll with the rule restored. 

$ temporal operator namespace update --address localhost:17233 -n ns2 --active-cluster cloud
$ HANDED_OFF="ns1 ns2" bin/gen-config
# roll Temporal Proxy
$ temporal workflow signal --address localhost:7233 -n ns2 -w pre-1 --name ping --input '"written on cloud"'

$ temporal operator namespace update --address localhost:27233 -n ns2.acct --active-cluster self-hosted
$ HANDED_OFF=ns1 bin/gen-config
# roll Temporal Proxy
$ temporal workflow signal --address localhost:7233 -n ns2 -w pre-1 --name ping --input '"back on self-hosted"'
$ bin/payloads self-hosted ns2 pre-1
$ bin/metrics
Expect
  • Both pings echoed: the first at v2, written by cloud, the second at v11, written by self-hosted after failing back.
  • No errors in bin/metrics.
  • In bin/payloads, every event cloud wrote stored on self-hosted as json/plain, while the events either side of them are sealed under ns:ns2.

That last point is s2s-proxy working as designed: it opens payloads arriving from the peer, Temporal Proxy's included. But it means a Namespace that fails back has the history written on Cloud in cleartext in the self-hosted Temporal Service's database, which Phase 1's "everything written from here on is sealed" doesn't account for.

Opaque data

s2s-proxy runs with allowOpaquePlaintext: false, so any replication message carrying data it can't seal is refused and counted in enc_opaque_rejected_total. Which Temporal features produce such data on this server version is the open question, so there's no recipe here yet. To look for it, exercise the features you use in production on a replicated Namespace, and watch bin/metrics, the s2s-proxy log (docker compose logs -f s2s-self-hosted), and whether new history keeps reaching cloud. To see the other side of the setting, run ALLOW_OPAQUE_PLAINTEXT=true bin/gen-config and restart s2s-self-hosted, and opaque data is passed through and counted in enc_opaque_passthrough_total instead.

Reset and tear down

Stop the Worker and Temporal Proxy with Ctrl-C, then remove the containers. Each Temporal Service keeps its data inside its container, so this also wipes every Namespace and Workflow: 

$ docker compose down

To start over from Set up, also clear the generated configs and keys. Only ever delete the keys along with the Temporal Services' data, or the history they sealed stops opening: 

$ rm -rf generated

Things worth knowing

Found while building this, and worth carrying to the real migration:

  • A Worker left on the direct path fails Workflows. After Phase 1, a Worker still talking to the self-hosted Temporal Service directly receives sealed payloads it can't decode, and the Go SDK fails the Workflow execution for good, not just the task. Phase 1's "confirm nothing but Temporal Proxy calls it" is guarding against that, not only against unreadable payloads.
  • Failback stores Cloud's history in cleartext. s2s-proxy opens payloads arriving from the peer, so events written on Cloud land unsealed in the self-hosted Temporal Service after a rollback.
  • Adding a replica doesn't backfill. Only history written after --cluster cloud replicates on its own. Workflows that already exist need force-replication.
  • Reads against a passive Namespace are forwarded. With forwarding on, reading ns1.acct's history from cloud before handoff returns self-hosted's copy, sealed under K_ns1 by s2s-proxy on the way back. Add --grpc-meta xdc-redirection=false to see what cloud really holds, which is what bin/payloads does.
  • s2s-proxy takes a minute to serve. It binds its ports at once but waits a fixed minute (MuxManagerStartDelay) for its mux connection before serving them, so a port probe or pprof says it's ready too early. The compose healthcheck waits for its grpc_server_started metric instead.
  • A new remote cluster takes a while to be known. A Temporal Service reloads cluster metadata every minute by default, so a Namespace can't be replicated to a cluster added seconds ago (Invalid cluster name). The shared dynamic config here sets system.clusterMetadataRefreshInterval to 5 seconds.
  • Temporal Proxy drains for 5 seconds, not 30. The gateway drops long polls after 5 seconds rather than waiting them out; 30 seconds bounds the whole shutdown.
  • Labelled counters only appear once incremented, in both proxies. A counter missing from /metrics is zero.

Troubleshooting

Symptom Likely cause
cluster upsert fails with context deadline exceeded s2s-proxy isn't serving yet. Rerun docker compose up -d --wait and try again.
Invalid cluster name: cloud The Temporal Service hasn't reloaded cluster metadata since the upsert. Wait 5 seconds and retry.
bin/payloads cloud ... says workflow not found The Workflow predates the replica and hasn't been force-replicated yet, or force-replication ran before the Namespace reached cloud. Run it again.
vault_ops_total{result="unknown_key"} A key one proxy sealed with isn't in the other's config. Configs from different generated/keys files, most likely.
vault_ops_total{result="mismatch"} under strict A label disagrees: a missing or wrong s2s-proxy mapping, or a decode request naming ns1 instead of ns1.acct.
A proxy refuses to start with duplicate key id The same key under two names. bin/gen-config won't do this; a hand-edited config might.
