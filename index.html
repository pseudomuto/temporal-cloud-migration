Playbook

Migrating to Temporal Cloud

Move Namespaces from a self-hosted Temporal Service to Temporal Cloud one at a time, without a payload leaving the self-hosted side in cleartext.

Draft, 2026-10-20. This assumes s2s-proxy changes that haven't merged yet (#322 to #326), and the items under Confirm before starting haven't been tested end to end.

Config blocks marked live are generated from these and from your progress below. Prose uses ns1 as the example. Everything you enter or tick is saved in this browser only.

Two proxies share the work:

  • temporal-proxy carries Worker and Client traffic. Every Worker and Client points at its gateway once, before the migration starts, and never changes again. Handing a Namespace to Cloud is deleting its routing rule and a rolling restart.
  • s2s-proxy carries replication between the two Temporal Services, sealing admin traffic and replication streams on the way out.

The Temporal side of replication (connecting the Temporal Services through s2s-proxy, adding Cloud as a replica of each Namespace, and failing a Namespace over) is summarized here, not specified.

Assumptions

  • temporal-proxy is at v1.0.0 or later, the same version s2s-proxy builds on. That release has encryption.failures, encryption.namespaceBinding, and namespaces.bindingLabelsFrom, which the playbook relies on.
  • s2s-proxy includes temporalio/s2s-proxy#326 and the changes it builds on. Together they seal admin calls and replication streams, seal failure messages and stack traces the way temporal-proxy does, and bind payloads to the Namespace's name on the peer. s2s-proxy builds on temporal-proxy v1.0.0 (temporalio/s2s-proxy#327), so either proxy opens what the other sealed.
  • Each Namespace's Cloud name is its local name plus the account suffix, and so on.

What "no plaintext" covers

Both proxies seal payloads (Workflow and Activity inputs and results, signal and update arguments, memo, heartbeat details) and failure messages and stack traces. That is the guarantee: none of those leaves the self-hosted side readable.

It does not cover what a Temporal Service needs to read to do its job, which crosses as is:

  • Metadata. Workflow IDs, run IDs, Workflow and Activity type names, task queue names, Namespace names, timestamps, and retry policies.
  • Search attribute values. Both proxies skip search attributes when sealing (internal/proxy/codec.go here, interceptor/encryptor.go in s2s-proxy), because Cloud has to read them to answer visibility queries. Anything sensitive in a search attribute crosses in the clear. Audit them before starting.
  • Opaque admin data, covered under Phase 0. This is the one case where the guarantee is enforced by refusing to replicate, not by sealing.

Every sealed payload names the KEK that wrapped its DEK, and opening looks the KEK up by that ID across every key the vault holds (pkg/crypto/kek.go). So a key only needs to be listed somewhere in a proxy's config to be usable for opening; which Namespace it was listed under does not matter.

Keys

Each migrating Namespace gets a KMS key of its own, K_ns1 through K_ns5, and both proxies seal that Namespace's payloads with it. Two shared keys sit beside them:

  • K_ns1 and the rest, under encryption.overrides in both proxies, keyed by the local Namespace name. temporal-proxy seals the Namespace's Worker and Client traffic with it, and s2s-proxy seals the calls it forwards for that Namespace.
  • K_proxy, temporal-proxy's encryption.default.uri. A default key is required, and it seals whatever has no override: a Namespace created during the migration, a typo, and calls that name no Namespace.
  • K_repl, s2s-proxy's encryption.default.uri. Replication is sealed under it.

Replication isn't sealed per Namespace. s2s-proxy seals every admin message, replication included, under its replication key, whatever Namespace the task belongs to (replicationKey in interceptor/admin_encryptor.go). It knows each task's Namespace for binding, but not for choosing a key. So history written before temporal-proxy reaches Cloud under the shared K_repl, not under K_ns1. Revoking K_ns1 doesn't make that history unreadable; that takes revoking K_repl, which covers every Namespace. Payloads temporal-proxy sealed are passed through untouched, so they stay under K_ns1.

Both configs carry the same overrides

The two override maps must be identical: same Namespaces, same key URIs. A Namespace missing from s2s-proxy's map has its forwarded calls sealed under K_repl instead of its own key. One whose key differs is sealed under a key the other proxy may not hold, which fails with vault_ops_total{result="unknown_key"}. temporal-proxy needs K_repl because, once a Namespace is in Cloud, its history from before the migration was sealed by s2s-proxy. Without it, those payloads fail with vault_ops_total{result="unknown_key"}. s2s-proxy needs K_proxy only for failback, to open anything temporal-proxy sealed under its default on the way back into the self-hosted Temporal Service.

No key may appear twice in one proxy's config, across default, replication, overrides, and every decryptURIs: both proxies refuse to start with duplicate key id (pkg/crypto/kek.go). That is why each Namespace needs a distinct key, and why s2s-proxy sets no replication policy: without one, admin traffic is sealed under default, which is already K_repl, and naming K_repl in both would be a duplicate.

Namespace binding

With binding on, each sealed payload is labeled with a Namespace name, and under strict it opens only for that Namespace. Both proxies label with the name Cloud knows, , so the label is the same whoever sealed the payload and wherever it is read:

  • temporal-proxy labels with the Namespace's name on the routed upstream. The self-hosted upstream sets namespaces.bindingLabelsFrom: cloud, so payloads it seals for ns1 are labeled with cloud's name for it, and open under the same label after handoff. See Moving a Namespace between upstreams.
  • s2s-proxy labels with the Namespace's name on the peer, from its namespaceTranslation mappings. Replication tasks name their Namespace by ID, which s2s-proxy resolves with DescribeNamespace on the self-hosted Temporal Service. The label is still , but the payload is sealed under the replication key.

Both keys are new, and both proxies label from the first payload they seal, so no unlabeled payload ever exists. That is what lets the migration reach strict without the usual wait for unlabeled history to age out.

What strict costs during the migration

  • Cross-Namespace traffic is refused. See Phase 0. If any exists, both proxies stay on permissive.
  • Tools that read the self-hosted Temporal Service directly can't decode. Payloads there are labeled , but a tool talking to it directly names ns1, so the codec server answers 400 and the tool shows ciphertext. The fix is to point the tool at the gateway instead: temporal-proxy opens payloads on the way back, labels agree because bindingLabelsFrom applies to the request too, and no codec server is involved. For the self-hosted Web UI, set its Temporal address to the gateway. It then shows plaintext, and since each Namespace follows its routing rule, the same UI shows Cloud's copy once the Namespace is handed off. See Phase 0 step 5.

    For a tool that has to stay on the direct path, the CLI can name the Cloud name in the codec endpoint path, which takes precedence over the X-Namespace header it sends. Use the literal name, not {namespace}:

    A Web UI left on the direct path can't do that: its codec endpoint is one URL for every Namespace.
  • Mistakes become outages. A Namespace missing from s2s-proxy's namespaceTranslation is labeled ns1, and temporal-proxy refuses its replicated history once it is read from Cloud. A Namespace ID s2s-proxy can't resolve fails the replication message, and with it the stream, where permissive would fall back to the replication key's name and count it. The Phase 2 soak exists to catch both.

Teams that know they have no cross-Namespace traffic, and have moved every tool that reads payloads to the gateway, can start on strict and skip the soak.

Phase 0: inventory and decisions

Do these before touching any traffic.

  1. List the Namespaces. Ask the self-hosted Temporal Service directly, since nothing goes through temporal-proxy yet: 
    temporal operator namespace list --address temporal.internal:7233 -o json \
  | jq -r '.[] | [.namespaceInfo.name, .namespaceInfo.state, (.isGlobalNamespace // false)] | @tsv'
    Example output
    default          NAMESPACE_STATE_REGISTERED  false
temporal-system  NAMESPACE_STATE_REGISTERED  false
ns1              NAMESPACE_STATE_REGISTERED  false
...
    Reading the output
    • temporal-system belongs to the Temporal Service itself. It never migrates and needs no routing rule.
    • default exists on every Temporal Service. It needs a rule like any other Namespace if something uses it, and can be left out otherwise.
    • NAMESPACE_STATE_DEPRECATED Namespaces refuse new Workflows but still hold running ones, so decide whether each one moves or drains in place.
    • The third column says whether the Namespace is global. Only global Namespaces replicate, so any false that is migrating gets promoted in step 7.

    Registered isn't the same as used. Once Phase 1 is running, set metrics.labels.namespace: true for the migration and vault_ops_total broken down by namespace shows which Namespaces carry traffic. Turn it back off afterwards; see Labels and cardinality for why it is off by default.

    Enter the result in Namespaces to migrate at the top.
  2. Find opaque admin data. Some admin data can't be sealed: HSM and CHASM state, serialized tasks, and the like, which the receiving Temporal Service decodes itself. With encryption.allowOpaquePlaintext off, which "no plaintext" requires, s2s-proxy refuses any message carrying it.

    A refused unary call fails with Internal. A refused replication stream message ends the whole stream, not just the affected Workflow's part of it, and the peer sees Internal with "s2s-proxy could not seal or open a replication message; see its logs".

    s2s-proxy counts each refusal in enc_opaque_rejected_total, labeled by kind, and logs the kind and the field path. Neither names the Namespace or the Workflow, and since the stream ends, unrelated Workflows stall alongside the one that caused it. Find the cause from the Temporal side, from the replication tasks stuck at the head of the stalled stream.

    For each Namespace that turns up here, choose one:
    • Stop the feature producing it, and let the affected Workflows finish on the self-hosted side before failover.
    • Accept that those Workflows don't migrate.
    • Grant an exception and set allowOpaquePlaintext. It is a single s2s-proxy setting, so the exception covers every Namespace replicating through it.
    The counter only moves once replication is running, so the real inventory comes from Phase 2 with failover held back. Plan for this to be the step that sets the schedule.
  3. Audit search attributes for sensitive values, as above.
  4. Find cross-Namespace traffic: child Workflows started in another Namespace, signals sent from one, and Nexus operations that cross Namespaces. Their payloads carry the other Namespace's label, which strict refuses. temporal-proxy exempts Nexus but not the other two; s2s-proxy exempts none of them. Binding is one setting per proxy, so if any of this exists, both proxies stay on permissive for every Namespace, not just the ones involved.
  5. List everything that reaches the self-hosted Temporal Service directly: the Web UI, the temporal CLI, admin tooling, batch jobs. After Phase 1 they see binary/encrypted payloads. Move each one to the gateway where you can, the Web UI included: through the gateway, payloads open the same way they do for Workers, under any binding mode. Keep the codec server for whatever has to stay on the direct path, and see Namespace binding for why that path can't decode under strict.

    Through the gateway, anyone who can use the tool sees plaintext, the same exposure the codec server has. If the gateway has inbound auth, the Web UI server needs to send credentials it accepts. Namespace-less calls, such as the ListNamespaces the Web UI uses to list Namespaces, go to the system upstream; see Phase 4 step 1 for what changes when that moves to Cloud.

  6. Record each Namespace's retention period. The longest one decides when K_repl can be retired.
  7. Prepare both sides for replication. Promote every migrating Namespace that isn't global yet with temporal operator namespace update -n ns1 --promote-global. Promotion is one-way, so do it per Namespace as its turn approaches, not all at once. Then create the Cloud Namespaces as replicas, named , and an API key for temporal-proxy. Create the KMS keys too: K_proxy, K_repl, and one per Namespace from the key map. Grant each proxy only what Who holds what lists.

Phase 1: put temporal-proxy in front

Deploy temporal-proxy with encryption on. Cloud is the default upstream from the start, and each Namespace gets a rule pinning it to the self-hosted Temporal Service until its handoff. This block tracks your progress: handed-off Namespaces drop out of rules, and namespaceBinding flips once you switch to strict.

Generating the rules for many Namespaces

With more than a handful of Namespaces, generate the rules from the Phase 0 listing rather than typing them, then prune any you decided not to migrate:

temporal operator namespace list --address temporal.internal:7233 -o json \
  | jq -r '.[].namespaceInfo.name | select(. != "temporal-system")
           | "    - { <<: *self-hosted, match: { namespace: \(.) } }"'
Why rules for the self-hosted side rather than for Cloud

Each handoff removes a rule instead of adding one, so the config only shrinks, and the end state is the plain Cloud config with no rules. The cost is that a Namespace with no rule, whether a typo or one created during the migration, reaches Cloud rather than the self-hosted Temporal Service. It fails there rather than leaking, since it is still sealed, and the router metrics catch it (below). system stays on the self-hosted side until the end, because Namespace-less calls such as GetSystemInfo and ListNamespaces have to answer for the Namespaces still there.

Why encryption on now, rather than at the first handoff
  • Encryption in temporal-proxy is global; it can't be turned on for the cloud upstream alone (internal/dataplane/dataplane.go). Turning it on at the first handoff would start sealing the other Namespaces on the self-hosted side at that moment anyway.
  • With it on from the start, everything written from here on is sealed before it reaches the self-hosted Temporal Service, and each handoff later is a routing change with nothing else moving.
Why bindingLabelsFrom

Without it, the self-hosted upstream labels payloads ns1, and after handoff they are read back from Cloud under , which strict refuses. See Namespace binding.

Then

  1. Move Workers and Clients to the gateway, one application at a time.
  2. Watch vault_ops_total for errors and router_decisions_total{upstream="self-hosted"} climbing. router_decisions_total{upstream="cloud"} must stay at zero until the first handoff; anything else is a Namespace missing a rule.
  3. Confirm, from the self-hosted Temporal Service's own request metrics, that nothing but temporal-proxy and the tools listed in Phase 0 still calls it. Locking it down at the network so only temporal-proxy, s2s-proxy, and those tools can reach it turns "confirm" into "enforce".

Phase 2: replicate

Configure s2s-proxy's cluster connection. Encryption and Namespace translation are both per connection:

s2s-proxy cluster connectionlive

Payloads temporal-proxy already sealed are recognized as sealed and passed through, so they reach Cloud under the Namespace's own key. History from before Phase 1 is sealed under K_repl on its way out, and calls s2s-proxy forwards under the Namespace's key from its overrides. Either way, the label is .

s2s-proxy looks up each replication task's Namespace ID with DescribeNamespace on the self-hosted Temporal Service, and caches the answer per connection for five minutes. Whatever credentials it uses there must allow that call.

On the Temporal side: connect the two Temporal Services through s2s-proxy, add Cloud as a replica of each Namespace, and let replication catch up.

Before switching to strict, which is before the first handoff

  • enc_unresolved_namespaces_total on s2s-proxy has stayed at zero since replication started. Each increment is a payload labeled with the replication key's name instead of its Namespace's, which strict would refuse when it is read back. If it moved, fix the cause and judge readiness only on payloads sealed after that.
  • enc_unbound_opens_total and enc_namespace_mismatches_total on s2s-proxy, and vault_unbound_opens_total and vault_namespace_mismatches_total on temporal-proxy, are at zero. Mismatches from the self-hosted Web UI or CLI going through the codec server under ns1 are expected; see Namespace binding.
  • For each Namespace, a replicated Workflow opens in the Cloud UI with temporal-proxy's codec server configured. That proves both keys open and that s2s-proxy's mapping matches temporal-proxy's suffix rule, which nothing else checks before handoff. Check one started before Phase 1 (K_repl) and one after (the Namespace's key).
  • Set namespaceBinding: strict on both proxies and roll them. Switching back to permissive is always safe. Ticking this updates both live config blocks.

Before each handoff

  • enc_opaque_rejected_total is zero, or every refusal has a decision from Phase 0.
  • Replication lag is near zero.
  • The Cloud UI check above passes for this Namespace.

These are the Conditions column in the Phase 3 tracker.

Phase 3: hand off one Namespace

Repeat for each Namespace, lowest risk first, soaking between them. Work left to right in the tracker.

Handoff progress
Namespace 1. Conditions 2. Failed over 3. Rule removed, rolled 4. Verified Status
  1. Check the Phase 2 handoff conditions for this Namespace.
  2. Fail the Namespace over to Cloud on the Temporal side.
  3. Remove the Namespace's routing rule and roll temporal-proxy. With no rule, it falls through to the default upstream, cloud.
  4. Verify. router_decisions_total{upstream="cloud"} climbs, server_requests_total shows no sustained non-OK codes, and vault_ops_total shows no unknown_key, mismatch, or unbound results. unknown_key means a proxy is missing K_repl, or the Namespace's key differs between the two configs; mismatch means a label disagrees, most likely a missing or wrong s2s-proxy mapping.

Fail over first, then roll. In the other order, replicas already routing to Cloud reach a Namespace that is still passive there and get NamespaceNotActive until the failover lands. Failing over first leaves the not-yet-rolled replicas talking to a passive self-hosted Namespace, which works only if the self-hosted Temporal Service forwards those calls to Cloud through s2s-proxy. See Confirm before starting.

temporal-proxy has no hot reload, so the routing change is a rolling restart. Each replica drains in-flight calls on SIGTERM (30 seconds by default), and SDKs reconnect long polls on their own.

Rollback runs in the same order: fail the Namespace back to the self-hosted Temporal Service, then roll with the rule restored. s2s-proxy opens payloads on the way back in, temporal-proxy's included, because it holds each Namespace's key, and K_proxy for unwrap. In the tracker, untick the Namespace's steps from right to left.

Phase 4: finish

  1. Point system at Cloud, and drop the self-hosted upstream, the empty rules list, and the x-self-hosted anchor. Namespace-less calls need a fixed endpoint, so add a system upstream as in the Cloud example:
    Cloud rejects ListNamespaces, which the Web UI uses to list Namespaces. When the system upstream is Cloud, temporal-proxy rewrites it to CloudService.GetNamespaces on its own, using that upstream's API key, which needs permission to read Namespaces (see the ListNamespaces example). Keep the suffix rule on cloud-system: without it the reply names , the UI requests that name, and the cloud upstream's suffix turns it into .
  2. Disconnect replication and retire s2s-proxy, once you no longer want failback.
  3. Keep K_repl in temporal-proxy's decryptURIs. Every pre-migration payload in Cloud history is sealed with it, and labeled for its Namespace, so strict opens it.
  4. Retire K_repl once nothing sealed with it remains: every Workflow started before Phase 1 has closed, and the longest retention period from Phase 0 has passed since then, plus anything you still read from archives. A long-running Workflow keeps its K_repl payloads for as long as it runs.

Removing the self-hosted upstream in step 1 removes bindingLabelsFrom with it. Labels don't change, because every Namespace already routes to cloud, whose names were the labels all along.

Confirm before starting

These are assumptions the playbook leans on that haven't been tested end to end. Tick each once a rehearsal has shown it.

  • Forwarding from a passive Namespace. Which calls the self-hosted Temporal Service forwards to Cloud after failover, polls in particular, decides whether the Phase 3 roll is clean or shows a burst of errors. Rehearse on a test Namespace.
  • s2s-proxy failback. That payloads temporal-proxy sealed, under the Namespace's key or K_proxy, open on their way back into the self-hosted Temporal Service, with s2s-proxy holding the Namespace's key through its override and K_proxy for unwrap only.
  • Labels agree across the proxies. That a payload s2s-proxy sealed, labeled from its namespaceTranslation mapping, opens under strict in temporal-proxy through the cloud upstream, and that one temporal-proxy sealed through the self-hosted upstream with bindingLabelsFrom does too. Both are built to derive ; the Phase 2 Cloud UI check is the first place it is tested.
  • What a refused replication message does to the stream. s2s-proxy ends the stream with Internal. That the Temporal Service then reconnects and retries the same message, stalling everything behind it on that stream until the cause is fixed, is inferred, not observed. Rehearse with opaque data and allowOpaquePlaintext off to see how it shows up in replication lag.
  • The Web UI works fully through the gateway. The README lists the UI as a gateway client, but this playbook hasn't exercised it end to end: browsing, decoding, starting and signaling Workflows, before and after a handoff, and the Namespace list once system points at Cloud. Also check that the UI server calls nothing beyond WorkflowService and OperatorService, the gateway's default service allowlist.
